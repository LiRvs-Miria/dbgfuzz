# ptrfuzz 设计文档：架构

> 状态：草案（2026-11-18）。范围：ptrfuzz 内部如何工作——部件、通道、覆盖后端、符号化、crash 处理。ptrfuzz 为什么存在读[背景](../background.md)（English: [background.md](../background.md)）。English: [architecture.md](architecture.md)。

## 部件与部署

ptrfuzz 跑在工作站上；目标端跑一个小小的伴生程序 `lldb-server`（为设备交叉编译，Linux 目标可原生）。调试信息——ELF/DWARF 副本——是工作站资产。目标跑出厂的那个二进制：stripped release 完全没问题。

```
工作站                                            目标端
├─ 变异引擎                                        └─ lldb-server（伴生）
├─ 覆盖引擎                                            （Linux：基于 ptrace；
├─ 符号化（目标 ELF + DWARF 副本）                       RTOS/裸机：JTAG gdbserver）
├─ crash 处理（停止、捕获、重放）
└─ 报告（覆盖图、战役统计）
        ↑
   输入驱动（用户编写；TCP/UDP/串口/文件 shim）
```

## 两条通道，一个大脑

调试通道和输入通道永不互相通信。ptrfuzz 同时持有两条连接并编排时序；lldb-server 与输入驱动彼此不知道对方存在。

**输入通道就是真实攻击面。** fuzz 输入从目标的真实接口进入——网络、串口、文件——绝不走调试通道。从调试通道注入等于测调试路径，不是测目标。

**通道分离是永久设计**，不是实现巧合：任何模糊两条通道的未来特性（比如走调试器"加速"输入注入的 fast mode）设计上直接否决。

## 覆盖循环在调试通道上的跑法

调试通道讲标准的 LLDB 远程协议（GDB RSP 家族）。一轮循环：

1. `Z0` 包——在地址 X 下断点（软断点或硬断点）。
2. `c` 包——目标继续跑。
3. 输入通道——把 fuzz 用例写进真实接口。输入驱动是哑巴字节转发；全部智能在主机侧。
4. 等停止应答。停止包携带停止原因：
   - **命中断点** → `g` 包读寄存器（PC）→ 更新覆盖图 → 下一轮。
   - **信号（SIGSEGV/SIGBUS/SIGILL…）** → 这是 crash。不 detach、不 kill：进程保持在调试器控制下的停止态。这个停止的进程**就是** crash 现场。
5. crash 处理——`g` 读全部寄存器，`m` 读栈内存；主机侧回溯调用栈。现场支持逐步重放和状态检查。

crash 现场之所以"活"：进程一辈子都在调试器控制下。crash 只是让它停下，没有任何人 kill 它。

## 覆盖后端

覆盖分档；粒度与速度互相牵制，按战役配置选择：

| 后端 | 目标类型 | 代价 | 粒度 |
|---|---|---|---|
| 软断点（ptrace patch 文本段） | Linux 目标 | 中 | 函数/区域级 |
| 硬件断点 | 真实设备（flash/XN 目标） | 受限（ARM 仅 ~6–16 个槽位） | 函数级 |
| 单步 | 任意，仅关键路径 | 灾难级（~10² execs/s） | 指令级 |

flash/XN 目标注记：软断点需要 patch 可执行内存，代码放在写保护 flash 里时不可行——硬件断点是唯一选项，槽位稀缺使覆盖成为一种预算资源。

## 符号化

符号化发生在主机侧。工作流：在工作站上 `target create` 未 strip 的 ELF 副本，`gdb-remote` 连接；目标继续跑 stripped release 构建。地址→函数/行号解析是纯粹的主机侧 DWARF 解析；目标进程零配合、零符号携带。

**唯一危险的失败模式**：工作站的符号文件必须与设备上运行的二进制出自**同一次构建**。错配的 DWARF 不会报错——它会**静默地**给出错误的函数名。厂商控制自己的构建流水线，天然满足；拿不到同构建文件的纯逆向场景降级到地址链档——覆盖引导依然完整。

## crash 处理

crash = 一个不是我们断点的信号导致的停止。处理刻意朴素：

1. 保持 attach。停止的进程就是证据。
2. 捕获：通用寄存器、栈内存、触发输入。
3. 重放：从捕获的现场驱动逐步重放与状态 dump。
4. 捕获完成后战役才继续（或重启目标）。

## 约束与失败模式

- 远程单步很慢——每步一次协议往返。单步覆盖只留给关键路径；战役按设计就是定向/夜间的。
- 硬件断点槽位稀缺；真机上的覆盖粒度是预算资源，不是免费品。
- 目标机上的 `lldb-server` 本身是攻击面和占用：只进测试构建，绝不进生产镜像。
- 解释型目标超范围：跑得动解释器的环境，现有的解释器感知 fuzzer（Atheris 类）已经赢。
- harness 问题（把字节送进闭源目标）不在范围内；ptrfuzz 管输入通道之后的所有事。
