## 覆盖率引导模糊测试的原理——以及为什么它需要目标配合

模糊测试器生成输入、砸向目标。盲目地做，这是大海捞针。**覆盖率反馈**是让
它变聪明的东西：fuzzer 记录"每个输入执行到了哪些分支和函数"，把精力花在
探索了新东西的输入上。几乎所有生产级 fuzzer（libFuzzer、AFL、honggfuzz、
OSS-Fuzz）都是这么工作的。

关键限制：**目标必须自己上报覆盖率**。实践中这意味着用 sanitizer runtime
（ASan/UBSan/TSan）或至少覆盖计数器来编译目标——注入目标进程的代码和数据
，外加一个负责收集的 runtime 库。

## 受限目标的现实

大量有价值的目标做不到这一点：

- **嵌入式 Linux / 网关**——没有 ASan（内存预算、glibc 老旧），装不下插
  桩开销。
- **实时内核与板卡**——内核功能缺失（许多 arm64 RT 构建没有硬件调试寄存
  器的 ptrace regset），每线程只有 4–6 个硬件断点。
- **遗留闭源二进制**——无法重编译，根本加不进任何插桩。

全系统仿真（QEMU）到处都能跑——但慢 10–100 倍。结果就是今天的样子：**大
多数已部署的攻击面（工控器、OT/IoT 设备、固件）没有实用的覆盖率引导模糊
测试方案**。对协议解析器做盲变异，在那里就算得上"模糊测试"了。

## ptrfuzz 的答案

把覆盖率收集从目标里搬出来：

- **调试器侧后端**——从外部观测目标：`PTRACE_SINGLESTEP`（每条指令后陷
  入；普适但慢）或硬件断点（快但稀缺），可选经
  [symrepl](https://github.com/LiRvs-Miria/symrepl) 编排。零重编译。
- **编译器侧最小插桩**——LLVM pass 只产出覆盖位图，不带 ASan 类 runtime
  （位图在进程退出或经调试器读取）。快，但需要重编译。

与 libFuzzer 相同的覆盖率引导循环；不同的只是反馈来自哪里。从来没有过模
糊测试方案的目标，从此有了。

## 这是谁的工具

- **产品安全团队**：在真实出货的硬件上 fuzz 自家固件、网关、协议解析器。
- **OT / IoT 研究者**：审计主流工具够不到的设备类别。
- **嵌入式方向的 QA / 可靠性工程师**："找到让事件循环卡死的输入"与内存安
  全同等重要。

## 术语表

| 术语 | 含义 |
|---|---|
| 消毒器运行时（sanitizer runtime） | 编译器注入目标内部的库（ASan/UBSan/TSan），负责检测 bug 和上报覆盖率——受限目标恰恰承载不了它 |
| 覆盖图（coverage map） | 记录哪些分支或基本块被执行过的位图/计数器 |
| 单步（single-step） | 每条指令后陷入一次（`PTRACE_SINGLESTEP`）——任何目标都支持，慢几个数量级 |
| 硬件断点（hw breakpoint） | CPU 调试寄存器里的地址比较器——快但稀缺（典型 arm64 每线程 4–6 个） |
| 语料库（corpus） | fuzzer 保留并持续变异的"有价值输入"集合 |
