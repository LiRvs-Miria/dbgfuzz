# 背景：dbgfuzz 为什么存在

*五分钟读完。English: [background.md](background.md)。*

## 这活儿是什么

你手里有一个无法重编译的二进制。它跑在真实硬件上——IoT 设备、车规 ECU、PLC、RTOS 任务。你想往它身上扔输入，想知道这些输入真的跑到了哪些路径，还想在它崩溃时留住现场：调用栈、寄存器、内存，调试器停下来的原样。

没有源码。不能重编译。没有 sanitizer runtime。这个约束直接杀死标准工作流。

## 为什么标准工具都不行

**要源码的 fuzzer**（libFuzzer、带插桩的 AFL++）是吞吐量的黄金标准——前提是目标能重编译。闭源固件和第三方二进制直接出局。

**基于仿真的 fuzzing**（AFL++ QEMU 模式）能打裸二进制，但仿真是个模型，模型会漏：外设缺失或失真，时序不对，硬件状态根本不存在。x86 上你还能退回 Intel PT 在真实硅片上做 trace 覆盖；嵌入式 ARM 上没有便宜等价物——硬件 trace（ETM）需要大多数工程师没有的探针和目标设备。

**协议 fuzzer**（boofuzz 之类）往通道里生成结构化输入，能检测 hang 和 crash。但它们盲打：没有"哪些解析器状态被到达过"的反馈，变异全靠猜，正门之后的深层逻辑几乎打不到。

## 那个洞察

调试器本来就贴在问题空间上。凡是它够得着的进程，它都能单步；能下硬件断点；能不征求目标配合就读寄存器、dump 内存。

所以让它当 fuzzer 的**眼睛**——给无法插桩的目标提供调试器侧覆盖反馈——以及 fuzzer 的**手**——crash 触发时目标已经停在调试器里。现场不是一个等着你重放的输入文件，它是活着的进程：调用栈、寄存器、内存就地可查，并支持逐步重放。

## 架构（部署）

dbgfuzz 跑在你的工作站上。目标端跑一个小小的伴生程序——`lldb-server`——两者由调试通道连接。fuzz 输入走目标的**真实接口**（网络、串口、文件）：就是全世界攻击它会用的那扇门。两条通道，一个大脑：

```
工作站                                        目标端
├─ dbgfuzz                                   └─ lldb-server（伴生）
│    （fuzzer、覆盖、报告）
└─ 目标二进制 + 调试信息副本
        ← 调试通道：断点、停止、状态读取
        ← 输入通道（网络 / 串口）：真实攻击面
```

这个部署给你三样东西：

1. **设备保持干净。** 设备跑 stripped release 构建；调试信息副本放在你的工作站上。设备永远不需要携带符号。
2. **有没有调试信息都能工作。** 有，报告给函数和行号；没有，给地址链和反汇编。覆盖引导两种情况下都不受影响。
3. **crash 是捕获的，不是重现的。** 整个战役期间进程都在调试器控制下运行，crash 发生的瞬间目标已经停下，现场完好。对有状态的目标——同一台机器明天都可能复现不了同一个 crash——捕获是唯一可靠的取证方式。

## 各买方得到什么

- **设备/RTOS 厂商（SDL、CRA 合规）。** 构建一次，未 strip 产物留在自己这边；测试农场的设备跑 stripped release。夜间战役产出函数级调用栈的 crash 现场——战役报告同时兼作测试证据。
- **第三方固件安全研究员。** 哪里都没有符号？覆盖引导照样指挥 fuzzer，crash 现场以地址链+反汇编形式交付。有状态的设备可能永远复现不了同一个 crash——活捕获胜过重放。
- **OT/ICS 研究员（PLC 运行时、OPC UA 栈）。** attach 真实控制器或网关上的运行时，从真实协议口注入，在真实栈上拿到 crash 现场——而不是在一个扭曲设备的仿真器上。
- **验证补丁的响应者。** 把覆盖钉在 patch 区域，重放漏洞证明输入，断言崩溃路径已不可达——用状态重放支撑结论。

## 生态位，诚实地说

dbgfuzz 不和 libFuzzer/AFL++ 竞争。有源码、要吞吐，就用它们——快几个数量级。dbgfuzz 服务的是交集：

> **真机 + 闭源 + 覆盖引导 + 便宜 triage**

这个交集是真实存在的：固件安全研究、出厂二进制的厂商 SDL（EU CRA 之下 2027 年 12 月起是法律义务）、以运行时本身为靶的 ICS 运行时研究。

dbgfuzz **不是**：吞吐工具。真机上的调试器侧覆盖很慢，这是设计上就接受的——战役是定向的、夜间的，不是批量吞。输入通道 harness（把字节送进闭源目标）仍是用户的活；dbgfuzz 只管通道之后的所有事。
